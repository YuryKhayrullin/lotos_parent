# Frontend-архитектура Lotos Parent

## Цель

Кабинет показывает подтверждённые данные из `lotos_crm`: ближайшее занятие, расписание, посещаемость, остаток занятий и историю оплат. Визуальная основа — переданный макет: тёмная навигация, светлая рабочая область, крупная карточка ближайшей тренировки, недельный календарь и компактные показатели. На телефоне интерфейс становится одноколоночным с нижней навигацией.

Достижения, чат, справки, push-уведомления и срок действия абонемента не входят в первый выпуск: в CRM пока нет подтверждённой модели этих данных. Реальный кабинет не подставляет примерные значения.

## Стек

| Задача        | Решение                                        |
| ------------- | ---------------------------------------------- |
| Фреймворк     | Next.js 16 App Router                          |
| UI            | React 19, TypeScript strict                    |
| Стили         | Tailwind CSS 4, семантические CSS variables    |
| Иконки        | Lucide React                                   |
| Авторизация   | Better Auth, HttpOnly cookie                   |
| Данные        | Typed Next.js API/BFF, Zod на входных границах |
| Даты и деньги | Intl, строка копеек и BigInt                   |
| Состояние     | URL и локальный React state                    |
| Тесты         | Node contract tests и Playwright               |

На первом этапе не добавляем Redux, Zustand, React Query, shadcn или Material UI. Кабинет пока read-only, объём данных небольшой, а визуальный стиль нестандартный. Отдельный клиентский cache понадобится с появлением чата, загрузки справок или optimistic updates.

## Маршруты

```text
app/
  login/page.tsx
  activate/page.tsx
  (portal)/
    layout.tsx
    page.tsx
    schedule/page.tsx
    attendance/page.tsx
    subscription/page.tsx
    loading.tsx
    error.tsx
  api/auth/[...path]/route.ts
  api/parent/[...path]/route.ts
```

Разделы становятся настоящими URL. Back/Forward, обновление страницы и прямые ссылки сохраняют контекст.

```text
components/
  auth/
```

Общий provider отвечает за выбранного ребёнка, неделю, обновление данных и восстановление после ошибок. UI-примитивы не содержат бизнес-текст; правила статусов остаются в feature-компонентах.

## Поток данных

```text
Browser
  -> Next.js portal layout
  -> подписанный серверный шлюз lotos_parent
  -> API lotos_crm
  -> Better Auth session + роль parent + активный ParentChildLink
  -> Prisma
  -> единая Supabase PostgreSQL / public
```

1. Серверный layout проверяет сессию до показа приватного интерфейса. Неавторизованный пользователь попадает на `/login`.
2. Список детей и начальная карточка загружаются на сервере.
3. Переключение ребёнка и недели использует персональный API и отменяет предыдущий запрос.
4. Каждый запрос повторно проверяет связь родителя с ребёнком; параметр `child` сам по себе не даёт доступа.
5. Персональные ответы остаются `private, no-store` и `Vary: Cookie`.
6. При возвращении вкладки данные обновляются фоном. Ошибка обновления не заменяет уже показанные данные нулями.

## URL и состояние

- текущий раздел определяется маршрутом;
- выбранный ребёнок хранится в `child`, неделя — в `week=YYYY-MM-DD`;
- сервер всегда проверяет доступ к ребёнку;
- пароли, сессии, платежи и карточки не хранятся в `localStorage`;
- Back/Forward восстанавливает раздел, ребёнка и неделю.

## Экраны

### Главная

На телефоне: приветствие и ребёнок, ближайшая тренировка, остаток, неделя расписания, посещаемость, последняя оплата, филиал. На компьютере блоки формируют сетку как в макете.

Карточка занятия показывает дату, время в таймзоне филиала, место, тренера и статус из CRM. Наступление времени само по себе не означает, что тренировка проведена.

### Расписание

Переключение недель, группировка по дням, статусы «по расписанию», «проведено», «отменено», карточка с тренером и местом, спокойное пустое состояние.

### Посещаемость

Процент по отмеченным занятиям за 30 дней, количества «был», «не был», «ожидает отметки» и хронологическая история. Отмены не влияют на процент.

### Абонемент

Текущий остаток, направление, план в неделю, последняя оплата и постраничная история: сумма, дата и начисленные занятия. Не показываем вымышленные срок действия и знаменатель пакета.

## Адаптивность

- 360–767 px: одна колонка, нижняя навигация, touch target от 44 px;
- 768–1023 px: одна или две колонки, нижняя навигация;
- от 1024 px: фиксированная боковая панель, контент до 1440 px;
- карточка занятия становится bottom sheet на телефоне;
- учитываются safe-area, `100dvh` и отсутствие горизонтального скролла.

## Визуальная система

Сохраняем navy, magenta, teal и светлый нейтральный фон из макета, но переносим цвета в семантические tokens. Используем системный или локальный шрифт без Google Fonts, чтобы интерфейс не зависел от внешнего CDN.

Каждый экран имеет skeleton, фоновое обновление, пустое состояние, красную ошибку с повтором, обработку потерянной сессии и доступные `aria-live` уведомления.

## Реализованный порядок

1. Дизайн-токены и UI-примитивы.
2. Общий shell, desktop sidebar и mobile navigation.
3. Отдельный `/login` и серверный auth gate.
4. Четыре настоящих маршрута вместо вкладок в одном компоненте.
5. Главная по макету и реальным CRM-контрактам.
6. Расписание и карточка занятия.
7. Посещаемость и абонемент с пагинацией.
8. Loading/error/empty/offline состояния и доступность.
9. Адаптивные правила для 360, 390, 768, 1024 и 1440 px.
10. Contract и integration проверки перед staging. Playwright user journeys запускаются в окружении с установленным Chromium.

## Критерий готовности

Родитель входит, видит только связанных детей, переключает ребёнка, открывает занятие, меняет неделю, проверяет посещаемость и оплаты, восстанавливается после ошибки и выходит. Все числа совпадают с карточкой ребёнка в `lotos_crm`; фиктивных функций и данных нет.
