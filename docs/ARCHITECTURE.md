# Архитектура кабинета родителя

## Принятое решение

Одна PostgreSQL Supabase, одна схема public, единые аккаунты Better Auth в lotos_crm. Два интерфейса Next.js/React/Tailwind развёртываются отдельно.

```text
Браузер сотрудника -> lotos_crm -> Prisma -> PostgreSQL/public
Браузер родителя -> lotos_parent/Next.js -> подписанный API lotos_crm -> та же PostgreSQL
```

## Владение данными

CRM управляет общими users, accounts, sessions, user_roles, parent_child_links и parent_invitations. Карточки детей clients и профили coaches сохраняются отдельно от учётных записей.

Поле users.role сохранено как совместимая основная роль работающей CRM. Триггер поддерживает соответствующую запись user_roles; parent можно добавить сотруднику без смены его основной роли. Старые ID, пароли и связи расписания сохраняются.

Все миграции находятся в lotos_crm/prisma/migrations. Родительский репозиторий больше не запускает собственные миграции.

## Граница доступа

Родительский API размещён под /api/parent/* основного бэкенда. До обработки запроса он проверяет подпись шлюза и срок запроса. Подпись не заменяет проверку родительской сессии и связи с ребёнком.

Доступ разрешён только активному аккаунту с ролью parent и сессией аудитории parent. Каждая операция над ребёнком проверяет parent_child_links и revoked_at. После чтения данные доступа проверяются повторно.

CRM-сессии и родительские сессии различаются audience и cookiePrefix. Переименование cookie не превращает родительскую сессию в сессию сотрудника.

Сервер lotos_parent не получает пароль базы, Better Auth secret или полномочия изменения бизнес-данных. Он принимает только разрешённые маршруты, ограничивает размер тела и время запроса. POST проверяет Origin. Перенаправления upstream запрещены.

## Контракт чтения

- GET /api/parent/children
- GET /api/parent/children/:id/overview?week=YYYY-MM-DD
- GET /api/parent/children/:id/payments?cursor=...

overview содержит остаток, ближайшее занятие, расписание выбранной недели, посещаемость за последние 30 календарных дней филиала, историю и первую страницу оплат.

Процент посещений рассчитывается по отмеченным завершившимся занятиям. Неотмеченные учитываются отдельно, отменённые исключаются. При отсутствии отметок процент равен null. Оплаты передаются в копейках строками, без потери точности.

Ответы используют private, no-store и Vary: Cookie. Внутренние комментарии, контакты других семей, служебный аудит и реквизиты аккаунтов в контракт не входят.

## Приглашения

Администратор явно подтверждает доступ к ребёнку. Поиск существующей учётной записи выполняется по нормализованному email; совпадение контакта без подтверждения не создаёт связь.

Приглашение действует 48 часов. В базе хранится SHA-256 токена. Ссылка использует URL-фрагмент, чтобы токен не передавался в запросе страницы. Экран активации убирает фрагмент из адресной строки.

Активация нового аккаунта атомарно создаёт credential, активирует пользователя и помечает приглашение использованным. Конкурентное использование допускает только одну успешную активацию.

Приглашение не сбрасывает пароль существующего аккаунта. Для сотрудника-родителя используется его действующий пароль. Неиспользованные приглашения отменяются при отзыве связи.

## Старое развёртывание

Прежняя отдельная родительская база и read-only подключение к CRM заменены этим решением. Облачные данные прежней базы автоматически не удаляются и не переносятся. При наличии рабочих аккаунтов нужен проверяемый перенос связей и приглашение пользователей; автоматическое объединение по одному контакту не выполняется.
