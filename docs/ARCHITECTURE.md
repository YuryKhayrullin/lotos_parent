# Архитектура Lotos Parent

## Данные и ответственность

lotos_crm записывает клиентов, конкретные занятия, состав группы, посещаемость, платежи и журнал начисления/списания. lotos_parent читает эти сведения через собственный сервер. Он не рассчитывает альтернативный баланс и не записывает изменения в CRM.

Браузер → Next.js API → Better Auth сессия → активная ParentChildLink → PostgreSQL CRM (SELECT).
Аккаунты, сессии, лимиты входа и связи находятся в схеме parent отдельной базы. Связь содержит ID клиента CRM и подтверждение оператора. Телефон/email клиента сами по себе не дают доступа.

## Источники

- Остаток: clients.remaining_lessons.
- Профиль и план: разрешённые поля clients + branches.
- Ближайшее занятие: активное lesson_enrollments, scheduled lessons, время окончания позже текущего момента.
- Календарь: конкретные lessons выбранной недели, активный состав выбранного ребёнка. Отмены видны явно.
- Посещаемость: attendance выбранного ребёнка. Процент за 30 календарных дней филиала = был / (был + не был). Будущие, отменённые и не отмеченные занятия исключены. Не отмеченные прошедшие занятия показаны отдельно.
- Оплаты: payments.paid_at, amount_minor, lessons_added. Денежные суммы передаются строкой в копейках для сохранения точности.
- В CRM нет отдельного действующего абонемента с датой окончания. total_lessons накопительное. Интерфейс не показывает вымышленные срок действия и знаменатель «из N».

## Доступ и отказоустойчивость

Для каждого ID сервер проверяет активного пользователя и связь до чтения CRM и повторно перед выдачей ответа. Чужой и несуществующий ребёнок получают одинаковый 404. Общий состав группы, контакты других родителей, внутренние комментарии и данные аккаунтов CRM не читаются.

Роль lotos_parent_reader имеет SELECT только на нужных колонках. Каждая операция выполняется в READ ONLY / REPEATABLE READ, с таймаутом. Приложение отказывается обслуживать чтение с ролью, имеющей права изменения CRM или создания объектов. Соединения повторно используются, на Vercel один слот каждого пула на процесс, TLS с проверкой сертификата.

Ответы персональные, private/no-store, Vary Cookie. Смена ребёнка отменяет предыдущий запрос и очищает экран. Ошибка базы показывает ошибку с повтором; примерные цифры не подставляются. Сервер не выводит секреты и SQL в публичные ответы.

Публичные auth-маршруты ограничены входом, выходом и проверкой сессии. Регистрация закрыта. POST проверяет Origin. Попытки входа атомарно ограничиваются по аккаунту, а на Vercel дополнительно по доверенному IP. Сессия продлевается с передачей Set-Cookie. В браузере нет токенов в localStorage.

## API

GET /api/parent/children — разрешённые карточки.
GET /api/parent/children/:id/overview?week=YYYY-MM-DD — баланс, неделя расписания, ближайшее занятие, статистика/история за 30 дней, первая страница оплат.
GET /api/parent/children/:id/payments?cursor=... — следующая страница оплат, 20 записей, ключ (paid_at,id).
GET /api/health — готовность двух подключений, без инфраструктурных деталей.
GET/POST /api/auth/... — только allowlist; остальные пути 404.

Календарь загружается по неделе в пределах года. Статистика агрегируется по всем отметкам периода; история ограничена 100 строками с явным предупреждением. Платежи имеют пагинацию.

## Выпуск

Новый Vercel и отдельная Supabase-база аккаунтов должны быть настроены до пилота. Нужно сверить карточки с CRM и проверить доступ из российских сетей без VPN; текущий адрес vercel.app ранее у пользователя не открывался без VPN. Создание проекта не решает сетевую доступность и не является публикацией в production.

Официальные инструкции: https://better-auth.com/docs/integrations/next и https://supabase.com/docs/guides/database/connecting-to-postgres.
