# Мониторинг LOTOS

Проверяются основной CRM, готовность PostgreSQL через CRM, публичный каталог Parent и свежесть резервной копии. Обычный DNS, без подмены IP и VPN. Запуск GitHub Actions каждые 5 минут; расписание best effort, не SLA.

Два последовательных сбоя открывают инцидент. После успешной проверки отправляется восстановление. Получатель настроен переменной OPS_EMAIL_TO: lotos.crm@yandex.ru. Для повторов письма сохраняется Message-ID; SMTP не гарантирует доставку ровно один раз.

## Дополнительные проверки

- Монитор проверяет также Parent health, формат JSON каталога и HTML страницы CRM. Ответ дольше 5 секунд считается деградацией; нужны два последовательных неуспешных прогона.
- Ручной Operations monitor → mode=check-only проверяет все сервисы без SMTP и без включения рассылки. Режим notify и расписание отправляют только ожидающие уведомления.
- Operations notification exercise отправляет два письма с пометкой «ПРОВЕРКА»: учебный сбой и восстановление. Рабочие сервисы и настоящий журнал инцидентов не изменяются.
- Cloud read performance: по понедельникам 08:23 UTC и вручную, 100 чтений каждого из четырёх публичных маршрутов, параллельность 4. Ни авторизации, ни записи в БД. Отчёт хранится 35 дней.
- Инженерные бюджеты p95/p99: CRM live 1500/3000 мс; ready 2500/5000; Parent health и catalog 3000/5000. Любая ошибка, недостаточная выборка или превышение порога проваливает проверку.

## Окно активации SMTP Яндекса

[Яндекс указывает 2–3 часа до активации нового пароля приложения](https://yandex.ru/support/id/ru/authorization/app-passwords.html?ysclid=l8twm8wtqd865436368). Контроль сразу после создания не доказывает, что пароль неверный.

OPS_SMTP_NOT_BEFORE задаёт самый ранний момент проверки. До него монитор продолжает проверять сервисы и сохраняет инциденты, SMTP не вызывается. После него автоматическая приёмка отправляет два учебных письма владельцу: сбой и восстановление. Принятый первый этап сохраняется, при повторе выполняется только оставшийся этап. Не больше трёх попыток с интервалом минимум 30 минут. После принятия обоих писем включается отправка настоящих ожидающих уведомлений. Это подтверждение SMTP accepted; фактическое получение владелец подтверждает отдельно.

Если все попытки отклонены, state содержит attention-required, workflow завершается ошибкой, дальнейшая SMTP-авторизация автоматически не повторяется. Новый пароль не нужно создавать по каждому 535.

GitHub Actions использует best-effort расписание. [В публичном репозитории расписания отключаются после 60 дней без активности](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows). При ежемесячной эксплуатационной проверке следует проверять state=active у Operations monitor и свежесть его последнего запуска.
