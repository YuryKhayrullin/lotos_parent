> Решение после обсуждения с тимлидом: одна база, одна схема public, общие аккаунты и основной API lotos_crm. Актуальное устройство: docs/ARCHITECTURE.md. Ниже сохранено исходное сравнение вариантов.

# Два варианта архитектуры `lotos_parent`

## Исходные условия

- `lotos_crm` — основная система и единственный источник данных о детях, расписании, посещаемости, остатках занятий, платежах и абонементах.
- `lotos_parent` — отдельный кабинет, в котором родитель видит только связанных с ним детей.
- ID родителя является внутренним идентификатором, а не паролем. Вход выполняется по телефону или email с паролем либо одноразовым кодом.
- Каждый запрос проверяет защищённую сессию и активную связь `ParentChildLink(parentUserId, crmClientId)`.

---

## Вариант 1. Одна база Supabase, две схемы

```text
Один Supabase / одна PostgreSQL
├── public — данные lotos_crm
└── parent
    ├── аккаунты и сессии родителей
    ├── приглашения
    └── ParentChildLink

lotos_crm    → роль с правами CRM
lotos_parent → отдельная ограниченная роль
```

Приложения остаются независимыми проектами и могут развёртываться как два проекта Vercel. Общей становится только физическая база данных.

### Создание кабинета

1. Администратор создаёт ребёнка в `lotos_crm` и указывает телефон или email родителя.
2. CRM нормализует контакт и ищет существующего родителя.
3. Если родитель уже существует, например у него второй ребёнок, повторная учётная запись не создаётся.
4. Для нового родителя создаётся приглашение.
5. Создаётся `ParentChildLink`.
6. Родитель активирует аккаунт и устанавливает пароль либо подтверждает вход одноразовым кодом.
7. `lotos_parent` показывает всех детей с активной связью.

Ребёнка, приглашение и связь можно создать в одной транзакции PostgreSQL.

### Доступ

- CRM управляет бизнес-данными и связями.
- Parent-приложение изменяет только свои аккаунты и сессии.
- Parent-приложение получает ограниченный `SELECT` к необходимым данным CRM.
- Parent-роль не может изменять клиентов, платежи, расписание или посещаемость.
- Знание ID ребёнка не предоставляет доступ без активного `ParentChildLink`.

### Плюсы

- Нет копирования и синхронизации.
- Изменения CRM сразу видны родителю.
- Единая транзакция при создании ребёнка.
- Проще резервное копирование и восстановление.
- Меньше секретов, подключений и точек отказа.
- Ниже стоимость разработки и эксплуатации.
- Существующая модель `ParentChildLink` подходит для этой архитектуры.

### Минусы

- Оба приложения зависят от одной базы.
- Миграции схем `public` и `parent` нужно согласовывать.
- Роли PostgreSQL необходимо тщательно настроить и протестировать.
- Ошибка администратора базы потенциально влияет на обе системы.

### План реализации

1. Добавить схему `parent` в существующий Supabase CRM.
2. Разместить в ней модели Better Auth, приглашения и `ParentChildLink`.
3. Создать отдельную роль `lotos_parent_runtime`.
4. Выдать ей запись в таблицы авторизации и ограниченное чтение CRM.
5. Добавить в создание клиента поиск или создание родителя и связь с ребёнком.
6. Реализовать приглашение и активацию.
7. Переключить `lotos_parent` на одно подключение.
8. Удалить конфигурацию второго физического Supabase.
9. Проверить сценарии с несколькими детьми, несколькими родителями и подменой ID.

## Вариант 2. Две отдельные базы Supabase

```text
Supabase CRM                         Supabase Parent
├── clients                         ├── parent users
├── lessons                         ├── sessions
├── attendance                      ├── invitations
├── payments                        └── ParentChildLink
└── integration outbox
       ▲                                  ▲
       └────── сервер lotos_parent ───────┘
```

Базы напрямую не соединяются. Сервер `lotos_parent` использует два подключения:

- запись в Parent DB для аккаунтов, сессий и связей;
- чтение CRM DB отдельной ролью без прав на изменение.

### Создание кабинета

Единой транзакции между двумя PostgreSQL нет, поэтому нужна событийная интеграция:

1. CRM создаёт ребёнка.
2. В своей транзакции CRM записывает событие `PARENT_ACCESS_REQUESTED` в outbox.
3. Обработчик отправляет событие в защищённый внутренний API `lotos_parent`.
4. Parent DB создаёт или находит родителя, приглашение и связь.
5. Ключ идемпотентности защищает от дубликатов.
6. При недоступности Parent DB событие повторяется позднее.

Бизнес-данные не копируются: после авторизации кабинет читает актуальные данные из CRM через read-only подключение.

### Плюсы

- Сильная изоляция систем и данных авторизации.
- Независимые миграции, резервные копии и масштабирование.
- Удобнее развивать кабинет как самостоятельную платформу.
- Компрометация Parent DB не даёт права изменять CRM.

### Минусы

- Нет единой транзакции.
- Возможна задержка появления кабинета.
- Нужны outbox, повторные попытки, идемпотентность и мониторинг.
- Два Supabase-проекта и два набора секретов.
- Выше стоимость разработки, тестирования и эксплуатации.
- Сложнее восстановление после частичных сбоев.

### План реализации

1. Оставить отдельную Parent DB.
2. Создать в CRM read-only роль.
3. Настроить два подключения в `lotos_parent`.
4. Добавить outbox в CRM.
5. Реализовать внутренний API приглашений и связей.
6. Добавить идемпотентность и повторную обработку.
7. Настроить мониторинг зависших событий.
8. Проверить отказ каждой базы и восстановление.

## Сравнение

| Критерий                   | Одна база, две схемы | Две базы                  |
| -------------------------- | -------------------- | ------------------------- |
| Сложность разработки       | Низкая               | Высокая                   |
| Единая транзакция          | Да                   | Нет                       |
| Актуальность данных        | Мгновенная           | Мгновенная при чтении CRM |
| Появление кабинета         | Мгновенно            | Возможна задержка         |
| Изоляция                   | Средняя              | Высокая                   |
| Секреты и подключения      | Меньше               | Больше                    |
| Стоимость эксплуатации     | Ниже                 | Выше                      |
| Независимые миграции       | Ограниченно          | Да                        |
| Текущий клуб               | Оптимально           | Избыточно                 |
| Независимая SaaS-платформа | Возможно             | Предпочтительно           |

## Рекомендация

Для текущего продукта рекомендуется **одна база Supabase с двумя схемами и отдельными ролями PostgreSQL**.

Это сохраняет `lotos_crm` единственным источником данных, устраняет синхронизацию и позволяет атомарно создать ребёнка, приглашение и связь. Безопасность обеспечивают отдельные роли базы, серверная сессия и обязательная проверка `ParentChildLink`.

Две базы стоит выбирать, если `lotos_parent` должен стать самостоятельным сервисом, подключаться к нескольким независимым CRM или развиваться отдельной командой.
